# 兩台工作站串機：為什麼要關掉 Domain Solver

## 結論

串接兩台工作站時，**分散的單位是「頻點」，不是「矩陣」**。

在 HPC 設定裡取消 Domain Solver、保留 Frequencies，是一般企業網路環境下
唯一能穩定跑完、而且加速幅度最大的配置。

---

## 兩種分散方式分的東西不一樣

|  | 頻點分散（採用） | Domain Solver／DDM（關閉） |
|---|---|---|
| 分什麼 | 掃頻的每個頻點發給不同機器，各自獨立解完整問題 | 同一個頻點的矩陣切成數塊，多台同時解 |
| 機器之間傳什麼 | 開工指令與最後的結果 | 每一次迭代都要交換邊界場 |
| 通訊特性 | 次數少、一次幾 MB | 次數極多、對延遲敏感 |
| 網路需求 | 一般 1 GbE 就夠 | 需要 InfiniBand 等級的低延遲互連 |
| 其中一台出狀況 | 只影響那個頻點，重跑該點即可 | 整個求解停住，而且不會跳錯誤訊息 |

---

## 現場實測（2026-09-15，兩台工作站以 1 GbE 直連）

| 項目 | 實測值 |
|---|---|
| 自適應網格第 9 次 pass（單機 shared memory） | 矩陣求解 **2 秒**，矩陣維度 142,438 |
| 同一個模型改成跨機解矩陣（DDM） | **17 分鐘零進度** |
| 卡住時，兩台的矩陣求解器 | 各只有 **1 個執行緒**、CPU 100%、記憶體完全不變 |
| 卡住時，兩台之間的網路流量 | 20 秒內：收 21 KB、送 33 KB |
| 卡住時，求解暫存目錄 | 17 分鐘內沒有任何檔案被寫入 |
| 改成頻點分散後 | 正常完成 |

**CPU 100% 但沒有資料交換、沒有檔案輸出、記憶體不增加**——這是 MPI 兩端互等的
空轉（Intel MPI 預設是 busy-wait，等待時一樣吃滿 CPU），不是在計算。

---

## 關掉它不會損失效能

求解時間的大宗在掃頻，不在自適應網格：

- **自適應網格**：每次 pass 的矩陣求解是 2 秒等級，跑在單機完全不是瓶頸。
- **掃頻**：頻點數 × 每點求解時間，這才是真正花時間的地方。

把掃頻分到兩台，等於把最耗時的那一段對半砍。這正是串機要買到的東西。

Domain Solver 想解決的是另一個問題——**單一頻點大到一台機器的記憶體裝不下**。
那是記憶體問題，不是速度問題，需要的硬體條件也完全不同。

---

## 什麼情況才該打開 Domain Solver

兩個條件要**同時**成立：

1. 單一頻點的模型大到一台機器的記憶體真的塞不下
2. 機器之間有 InfiniBand 或同等級的低延遲高頻寬互連

只有一般乙太網路時，DDM 常常比單機還慢，而且容易像上面那樣卡住不動。

---

## 設定位置

**Simulation → HPC Options → Analysis Configuration → Distribution Types**

| 項目 | 設定 |
|---|---|
| Frequencies | 勾選 |
| Domain Solver | 取消 |

**必須一併調整**：改成手動 HPC 設定之後，矩陣求解器不能留在自動選擇，
否則求解會直接失敗：

```
[error] Auto Select Direct/Iterative solver option is not supported
        by Manual HPC Settings -- Simulating on machine: <對端主機>
[error] Simulation completed with execution error on server: <對端主機>
```

改法：**在 Setup 上按右鍵 → Properties → Options 頁籤 → Solver**，
把 `Auto Select Direct/Iterative` 改成 **`Direct Solver`**。

（原本自動選擇的結果本來就是 Direct Solver，明確指定不會改變求解行為。）

---

## 給客戶的一句話版本

> 兩台機器是用「各自負責不同頻點」的方式分工，不是「合力解同一個頻點」。
> 前者只需要一般網路就能穩定運作，而且掃頻時間直接對半；
> 後者要求機房等級的低延遲互連，在一般網路上反而會拖慢甚至停住。
