# 修復動作與復原規格

搭配 [修復工具設計](修復工具設計.md)。這一份把每個動作的**正向操作**與**復原操作**逐一定死。

**核心規則：能不能寫出復原操作，就是一個動作能不能被自動化的判準。**
本文件裡任何一個動作，只要復原欄位寫不出來，就必須降級成「只印指令讓人自己執行」。

---

## 四條通則

### 1. 檔案類動作一律「備份位元組、還原位元組」

不要試圖用「反向編輯」還原檔案——那會受編碼、換行、BOM 影響。
直接複製整個檔案，還原時整個蓋回去。精確而且一定做得到。

備份完**必須驗證雜湊**。沒驗證過的備份不算備份。

### 2. 建立型動作只移除自己建立的東西

新增防火牆規則、新增 hosts 行這類動作，建立時要打上可辨識的標記
（`Ansys-Diag-<案件編號>`），復原時**只依標記移除**。
絕不依「看起來像我們會建的規則」去猜，客戶原有的設定不能碰。

建立前先檢查同名物件是否已存在。已存在就不建立、也不接管——那不是我們的東西。

### 3. 讀不到原值的設定，只在原值為空時才准動

`LicensingSettings web elastic list` 不會回傳 PIN（實測回傳空字串），
所以**無法捕捉原本的 CLS 憑證**。這代表如果客戶原本就設了另一組 CLS，
我們改掉之後還原不回去。

因此這類動作**只在「目前未設定」時才允許執行**——此時的復原操作是「清除」，
那是做得到的。原本已有設定的情況一律轉人工。

### 4. undo 腳本必須能獨立運作

`undo-<時間戳>.ps1` 不可以相依於修復工具本體或計畫檔——那兩個可能已經被刪掉了。
它必須是一支只靠備份資料夾就能跑完的純 PowerShell 腳本。

### 5. 不要委託給「會在你沒指定的位置動手」的工具

**開發時實際踩到的**：`set-license-server` 原本設計成優先呼叫官方的
`LicensingSettings.exe fnp server set --mode installation`，理由是「官方工具比較保險」。

結果那支工具**完全不理會 `ANSYSLIC_DIR`**，一律寫進它自己認定的安裝位置。
在隔離目錄下測試時，它跳出隔離區，把開發機真正在用的 `ansyslmd.ini` 覆蓋掉了——
而備份與 undo 都指向我們**以為**會被改的那個檔案。

也就是說：**動作看起來成功了，備份看起來做了，undo 也產生了，但回滾完全無效**，
因為被改的根本不是被備份的那個檔案。

原則：**正向操作碰的檔案，必須與備份、undo 碰的是同一個。**
做不到這點的外部工具就不要用，寧可自己直接寫檔——正向與復原對稱，
才談得上可復原。

## Tier 1：可自動修

### `set-license-server` 設定授權伺服器指向

| | |
| --- | --- |
| **正向** | **直接寫入 `ansyslmd.ini`**，改寫 `SERVER=` 行並保留其餘行（例如 `ANSYS_ELASTIC_CLS`） |
| **需捕捉** | `ansyslmd.ini` 完整位元組，以及「檔案原本是否存在」 |
| **復原** | 把位元組整個蓋回去；原本不存在就刪掉 |
| **驗證** | 讀回 `ansyslmd.ini`，`SERVER=` 行包含目標值 |

**不要呼叫 `LicensingSettings.exe fnp server set`**——見通則 5，那支工具會寫到
它自己認定的位置，不理會 `ANSYSLIC_DIR`，導致備份與實際被改的檔案不是同一個。

**為什麼復原是還原檔案而不是重下一次設定指令**：原本可能一台伺服器都沒有，
而設定指令不接受空輸入，那樣就還原不回去。還原檔案沒有這個問題。

編碼用 ANSI（`[System.Text.Encoding]::Default`）。授權相關設定檔用 UTF-8 可能被誤讀。

---

### `remove-stale-env` 刪除殘留的環境變數

| | |
| --- | --- |
| **正向** | `[Environment]::SetEnvironmentVariable($name, $null, $scope)` |
| **需捕捉** | 變數名、值、**scope（Machine / User 都要查）** |
| **復原** | `SetEnvironmentVariable($name, $oldValue, $scope)` |
| **驗證** | 兩個 scope 都查不到該變數 |

**陷阱：同一個變數可能同時存在於 Machine 與 User 兩個 scope 且值不同。**
只捕捉其中一個，復原時會把另一個弄丟。兩個都要查、都要記、都要還原。

環境變數的變更**要新的行程才會生效**，所以驗證不能在同一個 PowerShell 行程裡讀
`$env:`，要重新查註冊表或另開行程。這一點也要寫進給客戶的說明：
「已開啟的 Ansys 程式需要重新啟動才會套用」。

---

### `remove-user-ini` 刪除使用者層級的 ansyslmd.ini

| | |
| --- | --- |
| **正向** | 刪除 `%AppData%\.ansys_licensing\ansyslmd.ini` |
| **需捕捉** | 該檔案完整位元組 |
| **復原** | 複製回原路徑 |
| **驗證** | 檔案不存在，且 `-printlicpath` 改讀全域設定 |

**只刪檔案，不要刪 `.ansys_licensing` 資料夾。** 那個資料夾可能還有別的東西，
而且刪目錄的復原比刪檔案複雜。

---

### `clear-license-cache` 清除本機授權快取

| | |
| --- | --- |
| **正向** | 清空 `AppData\Local\Ansys`、`AppData\Roaming\Ansys`、`license_files\backup\` |
| **需捕捉** | 整個資料夾複製到備份區 |
| **復原** | 複製回去 |
| **前置條件** | **待備份總量 ≤ 500 MB，且備份磁碟可用空間 ≥ 需求的兩倍** |

**超過上限就不執行，改列為人工項目。** 理由很直接：備份不了就復原不了，
復原不了就不該自動做（通則 1）。

這些目錄可能很大，所以大小檢查是必要的前置條件，不是可選的最佳化。

執行前必須確認**所有 Ansys 程式都已關閉**，否則檔案被鎖住會刪一半。

---

### `restart-license-manager` 重新啟動 License Manager

| | |
| --- | --- |
| **正向** | `Stop-Service` → 等待 → `Start-Service`（`ANSYS, Inc. License Manager CVD`，必要時含 `ANSYSLicensingTomcat`） |
| **需捕捉** | 服務名稱、`Status`、`StartType` |
| **復原** | 還原成捕捉到的狀態（原本是停止的就再停掉） |
| **驗證** | 服務為 Running，且 `netstat` 上 1055 由 `lmgrd` 監聽 |

**這個動作本質上會造成短暫中斷**——重啟期間所有人都取不到授權，
正在借出的動作可能失敗。所以：

- 變更說明書要明講「執行期間全公司會有數十秒無法取得授權」
- 客戶應選離峰時間執行
- 啟動後要等到 1055 真的在監聽才算成功，不能只看服務狀態

服務起不來時，**復原不是「再停一次」而是「盡力讓它回到原本能跑的狀態」**。
若原本就是停的，那停著就是正確結果；若原本在跑而現在起不來，那是真正的失敗，
要停下來明講並附 Debug Log 位置。

---

### `enable-elastic-licensing` 啟用雲端彈性授權

| | |
| --- | --- |
| **正向** | `LicensingSettings.exe web elastic enable` |
| **需捕捉** | `web elastic list` 的 JSON（`enabled`、`clsId`） |
| **復原** | 原本是 disabled 就 `web elastic disable` |
| **驗證** | `web elastic list` 的 `enabled` 為 true |

---

### `enable-elastic-service` 啟用 web-elastic 授權服務

| | |
| --- | --- |
| **正向** | `LicensingSettings.exe preferences service set …` |
| **需捕捉** | `preferences service list` 的完整 JSON（含順序與各自的 enable） |
| **復原** | 用捕捉到的內容原樣 `set` 回去 |
| **驗證** | `preferences service list` 中 `web-elastic` 的 `enable` 為 true |

**復原不可以用 `preferences service reset`。** 那是還原成**原廠預設**，
不是還原成**客戶原本的狀態**。客戶可能刻意調過順序，reset 會把那個設定弄丟。

## Tier 2：需逐項明確授權

### `add-firewall-rules` 新增防火牆例外

| | |
| --- | --- |
| **正向** | `New-NetFirewallRule -DisplayName "Ansys-Diag-<案件編號> <項目>" …` |
| **需捕捉** | 我們建立的規則名稱清單；以及建立前同名規則是否已存在 |
| **復原** | `Remove-NetFirewallRule -DisplayName "Ansys-Diag-<案件編號>*"` |
| **驗證** | 從用戶端 `Test-NetConnection <伺服器> -Port 1055` 成功 |

**只移除自己建立的規則**（通則 2）。名稱一律帶案件編號前綴，
復原時依前綴比對，客戶原有的規則不會被碰到。

建立前若已有同名規則 → 不建立、不接管，記為「已符合，略過」。

**客戶的防火牆可能由網域群組原則統一管理**，此時本機新增的規則會被 GPO 覆蓋。
驗證失敗且偵測到 GPO 管理時，要明講「需由貴司網域管理者處理」，不要反覆嘗試。

---

### `add-hosts-entry` 新增 hosts 檔對應

| | |
| --- | --- |
| **正向** | 在 `C:\Windows\System32\drivers\etc\hosts` 附加一行，並加上標記註解 |
| **需捕捉** | hosts 檔完整位元組 |
| **復原** | 位元組整個蓋回去 |
| **驗證** | `Resolve-DnsName` 或 `ping` 解析得到正確 IP |

寫入格式：

```
# Ansys-Diag-<案件編號> 由虎門科技診斷工具新增於 <日期>
192.168.1.100    LICSRV01
```

即使復原採「整檔還原」，仍要寫這個標記——**讓人日後看得懂這行是誰加的**。

**IP 位址不能由工具猜。** 它必須來自解決包（我方在產生計畫時填入），
沒有這個參數就不產生這個動作。

hosts 檔沒有副檔名，還原時要注意不要被存成 `hosts.txt`。

---

### `install-license-file` 安裝或更換 License 檔案

| | |
| --- | --- |
| **正向** | 把新的 `.lic` 放進 `license_files\`，再透過 License Management Center 執行 Reread / Restart |
| **需捕捉** | **整個 `license_files` 目錄** |
| **復原** | 還原整個目錄，再 Reread / Restart |
| **驗證** | `lmutil lmstat -c` 顯示伺服器與 vendor daemon 都 UP；指定的 feature 可 checkout |

風險最高的 Tier 2 動作——**裝錯版本會讓原本還能用的部分也不能用**。所以：

- 新的 `.lic` 由解決包提供，工具不自己去任何地方抓
- 放進去之前先檢查 `SERVER` 行的主機名稱與 HostID 是否與本機相符，不符就中止
- 備份是整個目錄，不是單一檔案（可能有多個 `.lic`）

---

### `import-cls-credential` 匯入 CLS 憑證

| | |
| --- | --- |
| **正向** | `LicensingSettings.exe web elastic set --input <json 檔>` |
| **需捕捉** | `web elastic list` 的 `enabled` 與 `clsId`（**PIN 讀不到**） |
| **復原** | 清除設定（`web elastic disable` + 清空 clsId） |
| **前置條件** | **目前的 `clsId` 必須為空，否則不執行** |
| **驗證** | `web elastic list` 的 `clsId` 非空且 `enabled` 為 true |

這是通則 3 的典型案例。`web elastic list` 不回傳 PIN，所以原本已有憑證時我們
**還原不回去**，這種情況一律轉人工。

**憑證內容絕不寫進日誌或報告。** `.json` 憑證檔本身也不留在客戶機器上，
用完即刪。

## 複合動作：`restore-from-baseline`

這個**不是執行器的動作，而是解決包產生器的概念**。

產生計畫時，把基線差異展開成具體的原生動作：

```
基線差異：ansyslmd.ini 的 SERVER 從 SRV-A 變成 SRV-B
  → 展開成 set-license-server，參數 servers = ["1055@SRV-A"]
```

這樣做的理由：

- 執行器只需要實作原生動作，不必理解基線
- 計畫檔上客戶看到的是**具體會改什麼**，不是抽象的「還原成基線」
- 每個展開後的動作都有自己明確的 undo

執行器**不認得 `restore-from-baseline` 這個 id**，計畫裡出現就報錯。

## Tier 3：不實作，但要說清楚為什麼

這三個動作有 id，是為了讓報告能明確說「此項無法自動修復」而不是留白。
執行器看到 Tier 3 的動作**一律拒絕整份計畫**（不是略過該項——出現這種動作
代表計畫產生有問題）。

| 動作 | 為什麼不自動化 | 該怎麼處理 |
| --- | --- | --- |
| `stop-conflicting-service` | 停掉占用 1055 的第三方服務會弄壞客戶的另一套軟體 | 由我方與客戶討論停哪一邊，或改埠號 |
| `change-flexnet-port` | 需要伺服器與所有用戶端同步改，單機改只會壞得更徹底 | 規劃為一次維護作業 |
| `reinstall-license-manager` | 影響全公司，失敗時沒有簡單退路 | 排定維護時間，由我方工程師執行 |

## 執行器的通用檢查

每個動作執行前，執行器一律做這幾件事：

1. **權限**：需要系統管理員的動作，權限不足就中止整份計畫（不是略過）
2. **冪等**：已是目標狀態就記「已符合，略過」，不重複執行
3. **前置條件**：本文件中列出的前置條件（大小上限、clsId 必須為空…）
4. **備份與驗證**：備份完成並驗證雜湊，才允許進入寫入階段
5. **undo 可產生**：產不出 undo 就不執行該動作

執行後：

6. **逐項驗證**：用本文件的「驗證」欄位判定
7. **失敗即回滾**（決策 3）
8. **回滾也失敗**：停下來，輸出目前狀態與人工復原步驟，要求聯絡我方
