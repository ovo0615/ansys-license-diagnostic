**狀態：基礎已實作。** 5 個 Tier 1 動作已完成並通過 30 項回歸測試；
Tier 2 尚未實作。進度見本文最後。

情境：客戶同意我方直接修改他的環境，讓授權連線恢復正常。

## 出發點：不要弄丟「唯讀」這個資產

現在這支診斷工具能被客戶資安部門放行，靠的是一句話——**本工具全程唯讀，不會修改貴司任何設定**。
一旦這句話變成「預設唯讀，但加個參數就會改」，審查標準立刻不同，而且是**整支工具**都不同。

所以修復功能做成**獨立的第二支工具**，不是診斷工具上的開關。

好處：診斷工具的唯讀聲明維持乾淨、兩者可分別授權、資安審查可分兩次做、
不會有人「不小心加了那個參數」。代價是多一個檔案要維護。值得。

## 流程：從診斷到解決包

```
 1. 客戶跑診斷（唯讀）                        → findings.json + 報告
 2. 客戶回傳報告
 3. 我方判讀，用 New-RepairPackage.ps1 產生解決包草案
 4. 我方人工複核並簽發
 5. 【閘門】把「變更說明書」寄給客戶，取得書面同意     ← 沒有同意就停在這裡
 6. 提供解決包（修復工具 + 計畫檔 + 變更說明書）
 7. 客戶執行 → 前置檢查 → 備份 → 產 undo → 執行 → 驗證
 8. 失敗自動回滾；成功則產出修復報告
 9. 客戶回傳修復報告，我方存查
```

**第 5 步是流程閘門，不是工具功能。** 工具管不到「有沒有拿到同意」，
所以這一步靠流程紀律：案件編號把「同意信 → 診斷報告 → 修復計畫 → 修復記錄」串成一條線。

### 解決包的內容

一個案件一包，`repair-<案件編號>.zip`：

| 檔案 | 用途 |
| --- | --- |
| `Repair-AnsysLicense.ps1` | 修復工具本體（每個案件都是同一份，經過測試的那份） |
| `執行修復.bat` | 啟動器 |
| `repair-plan.json` | **本案專屬**，限定這次可以做哪些動作 |
| `變更說明書.md` | 給客戶看的：會改什麼、為什麼、怎麼復原 |

**工具本體每個案件都相同**——這點很重要。若每次手寫一支客製腳本，等於每個案件都在跑
沒測過的程式碼。改成「測過的工具 + 當作資料的計畫檔」，受測的東西才會累積。

**沒有計畫檔，修復工具完全不做事。** 沒有「什麼都修一修」的模式。

## 防範改錯的風險

這一節是重點。把「可能出什麼錯」逐一列出來，每一項都要有對應的機制擋住。

### A. 我方判讀錯 → 開錯藥

| 機制 | 說明 |
| --- | --- |
| **只有【確定】能生成動作** | 這是**寫死在程式裡的硬性閘門**，不是政策。【可疑】與【需人工】的 finding 一律不產生動作，因為那些本來就是「工具不敢斷言」的東西 |
| 計畫由工具產生，不手寫 | `New-RepairPackage.ps1` 從 `findings.json` 推導，手寫 JSON 是新的錯誤來源 |
| 強制人工複核 | 草案要經過我方複核才能簽發；未複核的計畫檔缺少簽發欄位，工具會拒收 |

第一條是整套設計中投報率最高的一項——它直接沿用診斷工具已經做好的信心分級。
**工具不敢斷言的事，就不准自動去改。**

### B. 參數填錯 → 改成錯的值

| 機制 | 說明 |
| --- | --- |
| 參數只能來自觀測值或基線 | 伺服器名稱、埠號、路徑一律取自 `findings.json` 或 `expected.json`，不手打 |
| 簽發前做合理性驗證 | 主機名稱要解析得到、埠號要在合理範圍、路徑要存在、目標伺服器要真的活著 |
| 附變更前後對照表 | 每個動作都要能寫成「從 X 改成 Y」。寫不出來就不該自動做 |

### C. 跑錯機器、或翻出舊計畫又跑一次

`repair-plan.json` 綁三個欄位：

- `targetComputerName` — 機器名稱不符就拒絕執行
- `expiresAt` — 過期就拒絕執行（建議 7 天）
- `basedOnReportSha256` — 綁定到當初判讀的那份報告

### D. 機器狀態已經變了

診斷可能是前一天跑的。執行前**重新驗證**：

- 問題已經不存在 → **中止**，不要動它（擋掉「客戶自己修好了我們又改一次」）
- 現況與報告不符 → **中止**，要求重跑診斷後重新出包

### E. 執行到一半失敗 → 半殘狀態

| 機制 | 說明 |
| --- | --- |
| undo 先於寫入產生 | **產不出 undo 的動作就不執行。** 執行到一半失敗時才有東西可用 |
| 逐項執行、逐項記錄 | 一次一個動作，每步寫進 `repair-log.jsonl` |
| 失敗自動回滾 | 決策 3 |
| 回滾也失敗 → 停下來明講 | 不要再嘗試補救，直接輸出目前狀態與人工復原步驟，並要求聯絡我方 |
| 冪等 | 同一份計畫跑兩次結果相同。執行前先檢查是否已是目標狀態，是就記「已符合，略過」 |

### F. 修好了授權，卻弄壞別的東西

| 機制 | 說明 |
| --- | --- |
| Tier 分級（見下節） | 影響半徑超出 Ansys 的動作一律 Tier 3，永不自動化 |
| 計畫中明列影響半徑 | 每個動作要寫清楚「會影響誰」，客戶同意時才知道自己同意了什麼 |
| 事後不只驗授權 | 也確認被碰過的服務、防火牆設定檔仍正常，沒有連帶損害 |

### G. 責任歸屬

- 客戶書面同意在前（決策 2）
- `repair-log.jsonl` 留在客戶機器，append-only
- 修復報告回傳我方存查
- 出事要能回答：**誰、什麼時候、依據哪份授權、改了什麼、怎麼復原**

## 動作分級

判準是**出錯時的影響半徑**，不是修改的難易度。

### Tier 1：可自動修（只影響 Ansys、只影響本機、可逆）

| 動作 | 復原方式 |
| --- | --- |
| 刪除殘留環境變數（`ANSYSLMD_LICENSE_FILE`、`ANSYSLI_SERVERS`、`ANSYSLI_LCP`、`ANSYSLI_ELASTIC`） | 記錄原值，還原時寫回 |
| 刪除使用者層級 `%AppData%\.ansys_licensing\ansyslmd.ini` | 備份後刪除 |
| 清除 `AppData\Local\Ansys`、`AppData\Roaming\Ansys` 授權快取 | 整個資料夾先備份 |
| 清除 `license_files\backup\` 內容 | 備份 |
| 設定 `ansyslmd.ini` 的 `SERVER=`（**直接寫檔**，見復原規格通則 5） | 備份原檔位元組 |
| 重新啟動 Ansys License Manager 服務 | 重啟本身即可逆 |

### Tier 2：需逐項明確授權（動到機器層級設定）

| 動作 | 為什麼要單獨授權 |
| --- | --- |
| 新增防火牆規則（`lmgrd`、`ansyslmd`、`ansyscl`、TCP 1055） | 可能牴觸客戶資安政策，且常由網域群組原則統一管理 |
| 修改 `hosts` 檔 | 影響全機名稱解析，不只 Ansys |
| 安裝／更換 License 檔案 | 需先備份舊檔；裝錯版本會讓原本能用的也不能用 |

### Tier 3：永不自動化

| 動作 | 為什麼 |
| --- | --- |
| **停用占用 1055 的第三方服務** | **會弄壞客戶的另一套軟體。** 停掉 `ptc_d` 等於讓對方全公司的 Creo 停擺 |
| 更改 FlexNet 埠號 | 需要伺服器與**所有**用戶端同步改，單機改只會壞得更徹底 |
| 移除／重新安裝 License Manager | 影響全公司，失敗時沒有簡單退路 |
| 任何需要重新開機的動作 | 客戶要自己排時間 |

> **我們最經典的案例（1055 被 `ptc_d.exe` 占用）正好落在 Tier 3。**
> 這不是設計缺陷，是正確結果——那個案子的正解是跟客戶討論停哪一邊、或改埠號，
> 這需要人做決定。工具能做的是**把根因指得非常清楚**，讓那個決定好做。

## 執行流程

```
1. 前置檢查   權限（依實際目標判斷，不是寫死的）
              計畫適用於這台機器、未過期、有簽發欄位
              重新驗證問題是否仍然存在      ← 不存在就中止
2. 建立快照   所有將被更動的檔案、環境變數值、服務狀態
              存進 repair-backup-<時間戳>\
3. 產生 undo  在任何寫入「之前」產生 undo-<時間戳>.ps1
              產不出來就不執行該動作
4. 逐項執行   一次一個，每步寫進 repair-log.jsonl
5. 驗證       重跑診斷的對應檢查
6. 失敗處理   自動回滾；回滾也失敗就停下來明講
7. 產出報告   改了什麼、結果如何、undo 指令是什麼
```

## `repair-plan.json`

```json
{
  "schemaVersion": 1,
  "caseId": "ACME-20260828",
  "issuedBy": "cae-support@cadmen.com",
  "issuedAt": "2026-08-28T10:00:00+08:00",
  "expiresAt": "2026-09-04T00:00:00+08:00",
  "reviewedBy": "工程師姓名",
  "customerApproval": "2026-08-28 客戶 IT 回信同意",
  "targetComputerName": "ACME-LICSRV",
  "basedOnReportSha256": "…",
  "onVerifyFailure": "rollback",
  "actions": [
    {
      "id": "remove-stale-env",
      "tier": 1,
      "params": { "names": ["ANSYSLMD_LICENSE_FILE", "ANSYSLI_LCP"] },
      "before": { "ANSYSLMD_LICENSE_FILE": "1055@OLD-SRV" },
      "after":  { "ANSYSLMD_LICENSE_FILE": null },
      "impact": "只影響本機的 Ansys 授權查詢順序",
      "fromFinding": "殘留環境變數 ANSYSLMD_LICENSE_FILE",
      "findingLevel": "CONFIRMED"
    }
  ]
}
```

幾個關鍵：

- **`actions[].id` 是列舉值**，不是任意指令字串。工具只認得清單內的 id，
  出現未知 id 就拒絕整份計畫。**參數不接受可執行內容**——否則這份 JSON
  就變成遠端執行任意程式的管道。
- **`findingLevel` 必須是 `CONFIRMED`**，工具會再檢查一次。這是 A 節那道硬閘門的落地。
- **`before` / `after`** 讓變更說明書可以自動產生，客戶同意時看得到具體的值。
- `reviewedBy` 與 `customerApproval` 缺一不可，否則拒收。

## 對現有診斷工具的改動

**已完成（2026-08-29）。** 這三項都不需要 VM，所以先做掉了。

1. **`-Json` 輸出**：findings 以機器可讀格式輸出，供解決包產生器使用。
2. **`Fix` 欄位結構化**：51 個 finding 中有 27 個標上了 `FixAction`。
   自由文字保留給報告顯示，機器讀 `fixAction` / `fixTier` / `fixParams` / `fixOn`。
3. **基線即修復目標**：`restore-from-baseline` 動作已定義。
   `expected.json` 已記錄「正常時長什麼樣」，把設定還原成基線是定義清楚、
   風險低、價值高的修復動作——這是現有 `-SaveBaseline` 意外的加值。

### 那道硬閘門已經落地

JSON 輸出裡預先算好兩個清單，解決包產生器不必自己重新推導：

- **`actionable`** — 只收 `level == CONFIRMED` **且** `fixTier < 3` 的動作
- **`notAutomatable`** — Tier 3 的動作，單獨列出供人工處理

實測驗證過五種情況：CONFIRMED tier 1/2 納入、CONFIRMED tier 3 排除、
SUSPECT 即使 tier 1 也排除、MANUAL 排除、Tier 3 有被單獨列出。

### `fixOn`：這個動作要在哪一台機器做

從用戶端觀察到的伺服器問題（例如 vendor daemon 沒起來、遠端埠沒人聽），
修復動作必須在**伺服器**上執行。沒有這個欄位的話，解決包產生器會把它誤放進
用戶端的計畫裡，客戶跑了也不會有效果。目前有 5 個 finding 標為 `licenseServer`。

## 測試策略

**這是和診斷工具最不一樣的地方，必須先解決才能開工。**

診斷工具可以在活生生的機器上開發，因為它不寫入。修復工具不行——
它每一條路徑都會改東西，而錯誤的那條路徑正是最需要測的。

**需要一台可拋棄的測試機。沒有這個就不要開始寫修復工具本體。**

### 環境盤點結果（2026-08-29）

開發機為 Windows 11 **專業版**、韌體虛擬化已啟用、20 邏輯核心、32 GB 記憶體、
F 槽可用 1296 GB。Hyper-V 角色與 Windows Sandbox **都尚未安裝**，但兩者都只是
「啟用功能 + 重新開機」的距離。WSL 有，但那是 Linux，測不了這支 Windows 工具。

### 分兩階段，不必一開始就建大的

重新盤點後發現**約七成的邏輯不需要安裝 Ansys**：

| 待測項目 | 需要 Ansys License Manager？ |
| --- | --- |
| 計畫解析、undo 產生、回滾、冪等性 | 不需要 |
| 環境變數、防火牆、`hosts`、檔案類動作 | 不需要 |
| 使用者層級 ini、AppData 快取 | 不需要 |
| 重啟 License Manager 服務 | 需要 |
| 透過 `LicensingSettings` 改設定 | 需要 |
| 更換 License 檔案 | 需要 |

**階段一：Windows Sandbox**

```powershell
Enable-WindowsOptionalFeature -Online -FeatureName Containers-DisposableClientVM -All
```

每次啟動都是全新的 Windows，關掉就丟——最純粹的「可拋棄」，不可能污染。
適合反覆測最容易寫錯的那部分：計畫解析、undo、回滾、冪等性。
限制是沒有持久化，不適合裝 Ansys LM。

**階段二：Hyper-V**

```powershell
Enable-WindowsOptionalFeature -Online -FeatureName Microsoft-Hyper-V-All -All
```

有原生檢查點，正好對應「製造故障 → 修復 → 驗證 → 還原」的循環。
Guest 建議用 Windows 11 Enterprise 評估版（官方免費 90 天，可從檢查點無限次還原），
加上 Ansys LM 約需 60–80 GB。

測修復工具**不一定需要有效的授權**，多數情況只需要 License Manager 這個軟體存在，
好讓服務、檔案結構與 `LicensingSettings` CLI 都在。要做完整端到端驗證時，
再申請一組綁該 VM HostID 的短期授權。

兩者都需要系統管理員權限並重新開機。

配套：

- **`-WhatIf`**：沿用 PowerShell 慣例，做完所有檢查與計畫，就是不寫入。
  開發期間的主力，也是客戶敢按第一次的原因。
- **每個動作獨立測試**：在 VM 上人工製造該故障 → 修復 → 驗證 → 跑 undo →
  確認回到原狀。**undo 沒測過的動作不能上線。**
- **失敗注入**：測「執行到第 3 個動作時失敗」的回滾是否正確。
- **回歸清單**：每個動作一組「故障情境 → 預期結果」，改版時全部重跑。
