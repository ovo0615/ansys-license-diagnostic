# 修復工具設計規劃

**狀態：規劃中，尚未實作。**

情境：客戶同意我們用工具直接修改他的環境，讓授權連線恢復正常。

---

## 出發點：不要弄丟「唯讀」這個資產

現在這支診斷工具能被客戶資安部門放行，靠的是一句話——**本工具全程唯讀，不會修改貴司任何設定**。
一旦這句話變成「預設唯讀，但加個參數就會改」，審查標準立刻不同，而且是**整支工具**都不同。

所以第一個設計決定是：

> **修復功能做成獨立的第二支工具，不是診斷工具上的一個開關。**

好處：

- 診斷工具的唯讀聲明維持乾淨，繼續好過審查
- 兩支工具可以分開授權：只想診斷的客戶永遠不會拿到修復工具
- 資安審查可以分兩次做，先過診斷、再談修復
- 不會有人「不小心加了那個參數」

代價是多一個檔案要維護。值得。

---

## 架構

```
Check-AnsysLicense.ps1      診斷（唯讀）      → findings.json
                                                    │
                                        我方工程師判讀
                                                    │
                                             repair-plan.json  ← 我方簽發
                                                    │
Repair-AnsysLicense.ps1     修復（會寫入）    ← 只執行計畫裡列出的動作
                                                    │
                                             undo-<時間>.ps1  ← 執行前先產生
```

**關鍵設計：修復工具自己不做判斷。** 它只執行 `repair-plan.json` 裡明列的動作，
而那份計畫是我方工程師看過診斷報告後簽發的。

這樣做的理由：診斷可能誤判。讓一支會寫入的工具同時扮演「判斷要修什麼」和「動手修」
兩個角色，等於把誤判直接變成損害。中間插入人工判讀，誤判最多變成一次白跑。

## 兩種授權模式

### A. 委派模式（預設）

1. 客戶跑診斷 → 回傳 `findings.json`
2. 我方工程師判讀，用 `New-RepairPlan.ps1` 產生 `repair-plan.json`
3. 客戶把計畫檔和修復工具放一起跑
4. 工具核對計畫的適用對象與有效期，執行，產生報告與 undo 腳本

多一趟來回，但**那一趟來回就是安全機制**，而且本來就符合代理商的工作方式。

### B. 現場模式

我方工程師電話／遠端陪同時使用。加 `-Interactive`，工具逐項提出建議動作，
客戶 IT 逐項確認才執行。

```powershell
.\Repair-AnsysLicense.ps1 -Interactive
```

現場模式仍受動作分級限制——Tier 3 的動作**在任何模式下都不會執行**。

## 動作分級

分級的判準是**出錯時的影響半徑**，不是修改的難易度。

### Tier 1：可自動修（只影響 Ansys、只影響本機、可逆）

| 動作 | 復原方式 |
| --- | --- |
| 刪除殘留環境變數（`ANSYSLMD_LICENSE_FILE`、`ANSYSLI_SERVERS`、`ANSYSLI_LCP`、`ANSYSLI_ELASTIC`） | 記錄原值，還原時寫回 |
| 刪除使用者層級 `%AppData%\.ansys_licensing\ansyslmd.ini` | 備份後刪除 |
| 清除 `AppData\Local\Ansys`、`AppData\Roaming\Ansys` 授權快取 | 整個資料夾先備份 |
| 清除 `license_files\backup\` 內容 | 備份 |
| 設定 `ansyslmd.ini` 的 `SERVER=`（透過 `LicensingSettings fnp server set`） | 備份原檔 |
| 重新啟動 Ansys License Manager 服務 | 重啟本身即可逆 |

### Tier 2：需逐項明確授權（動到機器層級設定）

| 動作 | 為什麼要單獨授權 |
| --- | --- |
| 新增防火牆規則（`lmgrd`、`ansyslmd`、`ansyscl`、TCP 1055） | 可能牴觸客戶的資安政策，且常由網域群組原則統一管理 |
| 修改 `hosts` 檔 | 影響全機名稱解析，不只 Ansys |
| 安裝／更換 License 檔案 | 需先備份舊檔；裝錯版本會讓原本能用的也不能用 |

### Tier 3：永不自動化

| 動作 | 為什麼 |
| --- | --- |
| **停用占用 1055 的第三方服務** | **會弄壞客戶的另一套軟體。** 停掉 `ptc_d` 等於讓對方全公司的 Creo 停擺 |
| 更改 FlexNet 埠號 | 需要伺服器與**所有**用戶端同步改，單機改只會壞得更徹底 |
| 移除／重新安裝 License Manager | 影響全公司，且失敗時沒有簡單退路 |
| 任何需要重新開機的動作 | 客戶要自己排時間 |

> **注意：我們最經典的案例（1055 被 `ptc_d.exe` 占用）正好落在 Tier 3。**
> 這不是設計缺陷，是正確結果——那個案子的正解是跟客戶討論要停哪一邊、或改埠號，
> 這需要人做決定。工具能做的是**把根因指得非常清楚**，讓那個決定好做。

## 執行安全流程

每一次修復都走這七步，任何一步失敗就停下來：

```
1. 前置檢查   確認權限（多數動作需系統管理員）
              確認計畫適用於這台機器、未過期
              重新驗證問題是否仍然存在
2. 建立快照   把所有將被更動的檔案、環境變數值、服務狀態存進
              repair-backup-<時間戳>\
3. 產生 undo  執行任何寫入「之前」先產生 undo-<時間戳>.ps1
              產不出 undo 的動作就不執行
4. 逐項執行   一次一個動作，每一步寫進 repair-log.jsonl
5. 驗證       重跑診斷的對應檢查，確認問題真的解決
6. 失敗處理   驗證不過 → 自動回滾（或依計畫設定改為停下來問）
7. 產出報告   改了什麼、結果如何、undo 指令是什麼
```

### 第 1 步為什麼要重新驗證

診斷是幾小時前甚至前一天跑的，機器狀態可能已經變了。**若問題已經不存在就不要動它**——
這能擋掉「客戶自己修好了、我們又去改一次」這種製造新問題的情況。

### 第 3 步是整個設計的關鍵

**能不能表達出反向操作，就是一個動作能不能被自動化的判準。**
寫不出 undo 的動作，一律降級成「只產生指令讓人自己貼」。

undo 腳本必須在寫入**之前**產生，不是之後——執行到一半失敗時，才有東西可以用。

### 冪等性

同一份計畫跑兩次，結果要和跑一次相同。每個動作執行前先檢查是否已經是目標狀態，
是的話就跳過並記錄「已符合，略過」。

## `repair-plan.json`

```json
{
  "schemaVersion": 1,
  "caseId": "ACME-20260828",
  "issuedBy": "cae-support@cadmen.com",
  "issuedAt": "2026-08-28T10:00:00+08:00",
  "expiresAt": "2026-09-04T00:00:00+08:00",
  "targetComputerName": "ACME-LICSRV",
  "basedOnReportSha256": "…",
  "onVerifyFailure": "rollback",
  "actions": [
    {
      "id": "remove-stale-env",
      "tier": 1,
      "params": { "names": ["ANSYSLMD_LICENSE_FILE", "ANSYSLI_LCP"] },
      "reason": "殘留的環境變數會插到伺服器清單最前面，導致連到錯的伺服器"
    },
    {
      "id": "set-license-server",
      "tier": 1,
      "params": { "servers": ["1055@ACME-LICSRV"], "mode": "installation" },
      "reason": "用戶端指向已停用的舊伺服器"
    }
  ]
}
```

三個欄位是防呆的核心：

- **`targetComputerName`** — 防止把 A 機器的計畫跑在 B 機器上
- **`expiresAt`** — 防止半年後有人翻出舊計畫又跑一次
- **`basedOnReportSha256`** — 綁定到當初判讀的那份報告

`actions[].id` 是**列舉值**，不是任意指令字串。工具只認得清單內的動作 id，
計畫檔裡塞進未知 id 就拒絕執行。**不接受可執行內容當參數**——否則這份 JSON
就變成遠端執行任意程式的管道。

要不要加數位簽章？v1 先不用，`basedOnReportSha256` 加上人工核對已經夠。
若日後計畫檔會經過客戶轉寄多手，再考慮。

## 對現有診斷工具的改動

修復工具要能接手，診斷這邊得先補三件事：

1. **`-Json <路徑>` 輸出**：把 findings 以機器可讀格式輸出。
2. **`Fix` 欄位結構化**：目前是自由文字（55 處），對人很好讀但機器解析不了。
   改成同時帶 `FixAction`（動作 id）與 `FixParams`，自由文字保留給報告顯示。
3. **基線即修復目標**：`expected.json` 已經記錄了「正常時長什麼樣」，
   「把設定改回基線」是一個定義清楚、風險低、價值高的修復動作。
   這是現有 `-SaveBaseline` 意外的加值。

改動 1 和 3 對現有行為沒有影響。改動 2 要動到 55 處 `Add-Finding`，但都是加欄位，不改既有輸出。

## 測試策略

這是**和診斷工具最不一樣的地方**，必須先講清楚。

診斷工具可以在活生生的機器上開發，因為它不寫入。修復工具不行——
它的每一條路徑都會改東西，而且錯誤的那條路徑正是最需要測的。

**需要一台可拋棄的測試機（VM 快照）。** 沒有這個就不要開始寫。

配套：

- **`-WhatIf`**：沿用 PowerShell 慣例，做完所有檢查與計畫，就是不寫入。
  這是開發期間的主力，也是交付後客戶敢按第一次的原因。
- **每個動作獨立測試**：先在 VM 上人工製造該故障，跑修復，驗證，再跑 undo，
  確認回到原狀。**undo 沒測過的動作不能上線。**
- **失敗注入**：測「執行到第 3 個動作時失敗」的回滾是否正確。

## 稽核

代理商在客戶機器上做變更，要留得下記錄。

- `repair-log.jsonl` 留在客戶機器上（append-only，不覆寫）
- 每筆記錄：時間、案件編號、執行者帳號、動作 id、參數、結果、undo 指令
- 事後報告一併回傳我方存查

出事時要能回答「誰、在什麼時候、依據哪份授權、改了什麼」。

## 待決事項

以下三點需要你決定，會影響實作方向：

1. **修復工具要不要公開？**
   建議**不要**。診斷工具公開是資產，修復工具公開的效益低、風險高
   （被拿去亂改環境、以及責任歸屬）。建議放在私有 repo，
   沿用你現有的 `xxx` / `xxx-private` 配對模式。

2. **授權要不要落到書面？**
   建議**要**，而且要比 `repair-plan.json` 更前面一層——
   客戶的書面同意（一封回信即可）應該在簽發計畫之前取得，
   案件編號串起「同意信 → 診斷報告 → 修復計畫 → 修復記錄」。
   工具管不到這一段，但流程要定下來。

3. **`onVerifyFailure` 預設要 rollback 還是停下來問？**
   建議預設 **rollback**。修復失敗時，讓機器回到「原本壞的樣子」比停在
   「改到一半的樣子」好——前者我們知道怎麼處理，後者是全新的未知狀態。
